3. ROOT CAUSE
================================================================================

  See 11-order-tiebreak-rootcause.txt for the proof. In one sentence:

    tasks.created_at is DEFAULT now(), Postgres now() is transaction_timestamp()
    and is therefore constant for a whole transaction, so every fixture row
    built inside one withRollback() transaction carries an IDENTICAL created_at
    — and TASK_ORDER's final key, asc(tasks.createdAt), has no tie to break.

  The two assertions demand a total order over a tied key, so the row order is
  whatever the planner returns. 11 section 4 shows the SAME two rows coming
  back in the OPPOSITE order when only a planner setting is changed.

  Not affected: tests/api/ (11 section 5 — each HTTP request is its own
  transaction, so created_at values are distinct and the sort is total), and
  production (tasks are created one request at a time).

  Also worth noting for a later phase: TASK_ORDER has no final deterministic
  tie-break at all (e.g. asc(tasks.id)). Two tasks created in the same
  transaction will always sort arbitrarily, in any interface.
